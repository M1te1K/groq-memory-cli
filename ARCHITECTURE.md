# Архитектура CLI-бота с памятью

Выбран вариант 4: Python CLI, Groq Chat Completions и SQLite. Документ описывает реализованный код; состояние проверки на 17 октября 2026 года вынесено в [PUBLICATION_CHECK.md](PUBLICATION_CHECK.md). Установка и команды приведены в [README.md](README.md).

## Модули

| Модуль | Ответственность |
|---|---|
| `memory_agent/__main__.py`, `run.py` | Входы в один и тот же CLI |
| `cli.py` | argparse, обязательный `--user`, цикл ввода, команды, EOF/Ctrl+C |
| `config.py` | Чтение .env без изменения файла/окружения, приоритет окружения, проверка настроек |
| `agent.py` | Ход диалога, подготовка и commit памяти, история по профилям, ответы об ошибках |
| `llm.py` | Groq SDK, строгая JSON Schema извлечения, текстовый ответ, ограниченные повторы |
| `schemas.py` | Pydantic-модели, проверки источника/принадлежности фактов, нормализация, лимиты, план изменений |
| `memory.py` | SQLite, миграция, параметризованные операции с фактами и событиями, транзакции |
| `tests/` | Автотесты с временными БД и подставным LLM/HTTP; отдельный ручной live_smoke.py |

Прямые и тестовые зависимости определены в pyproject.toml; полное проверенное окружение фиксирует requirements.lock. Сборка использует setuptools. Конфигурация привязана к родительскому каталогу пакета (PROJECT_ROOT); рекомендуемый режим — editable-установка и запуск из корня исходников. run.py позволяет явно запустить CLI из другого каталога без зависимости от обнаружения editable .pth.

## Память и изоляция

Постоянные факты — записи SQLite с user_id, типом и значением. Типы: name, city, occupation, preference. Для имени, города и профессии уникальный слот (user_id, kind). Предпочтений может быть несколько; точные нормализованные повторы отсеивает код, смысловые повторы и противоречия должен распознать экстрактор. Профиль ограничен 50 фактами, каждый до 500 символов.

История живёт только в Agent.histories и разделена по user_id: последние 10 полных пар, не более 24 000 символов. Ответчик получает эту ограниченную историю; экстрактор — максимум два предыдущих сообщения пользователя по 2 000 символов для разрешения ссылок. Новым источником факта должно быть последнее сообщение. Логи не восстанавливают историю и не передаются LLM.

user_id задаёт приложение, модель не выбирает профиль. Все пользовательские чтения/изменения ограничены user_id и используют параметры SQL. Обновление/удаление по ID дополнительно проверяет принадлежность профилю. Локальная идентификация не является аутентификацией: любой пользователь терминала с доступом к БД может выбрать любой профиль. Данные не зашифрованы.

## Ход диалога и атомарность

1. CLI обрабатывает команды локально; обычный ввод передаёт агенту с активным user_id.
2. Агент читает снимок фактов этого профиля.
3. Groq извлекает operations: action, fact_id, kind, value, evidence. Pydantic запрещает лишние поля и проверяет форму результата.
4. Код проверяет ID, тип операции и дословное непрерывное evidence в последнем сообщении. Отсеивает очевидные цитаты, гипотезы, вопросы и чужие сведения. Для имени проверяется значение в источнике; для профессии — связь с текущим личным занятием, с учётом русских окончаний. Поддержаны имя со встречным вопросом и просьбы о кратком стиле.
5. Предварительная память строится в RAM. При отказе проверки разрешено одно повторное извлечение с безопасным фиксированным кодом причины. Пустое извлечение на явное «запомни» требует повторной проверки; известное значение нормализуется без дубля. Переполнение, API-ошибка и ошибка БД не запускают повтор проверки памяти.
6. Второй запрос Groq генерирует ответ с предварительным профилем и ограниченной историей. При удалении отдельного факта предыдущая история не передаётся, чтобы забытое значение не вернулось через неё.
7. commit_turn в BEGIN IMMEDIATE сверяет прежний снимок и атомарно сохраняет факты, операции и событие хода. Параллельная запись отклоняет устаревший снимок. Сеть работает вне транзакции.
8. Только после commit обновляется история и показывается ответ. При отдельном удалении факта история активного профиля очищается, включая ход удаления. Другие профили сохраняются.

Сообщение и ответ ограничены 8 000 символами; операции одного извлечения — 20. Частичное принятие операций не допускается. Сбой ответа или commit не оставляет частичные факты и не показывает обещание «запомнил». Проверки структуры и источника консервативны и не доказывают семантическую правильность произвольного текста: качество извлечения зависит от модели.

## SQLite и миграция

```sql
CREATE TABLE facts (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id TEXT NOT NULL,
    kind TEXT NOT NULL CHECK(kind IN ('name', 'city', 'occupation', 'preference')),
    value TEXT NOT NULL CHECK(length(value) BETWEEN 1 AND 500),
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
CREATE UNIQUE INDEX one_profile_slot ON facts(user_id, kind)
    WHERE kind IN ('name', 'city', 'occupation');
CREATE INDEX facts_by_user ON facts(user_id);
CREATE TABLE events (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    timestamp TEXT NOT NULL,
    user_id TEXT NOT NULL,
    event_type TEXT NOT NULL,
    payload_json TEXT NOT NULL
);
CREATE INDEX events_by_user ON events(user_id);
```

Открытие старой схемы без occupation пересоздаёт facts в одной транзакции. Сохраняются строки, ID, времена, AUTOINCREMENT (включая удалённые ID), явные индексы и триггеры; уникальный индекс слотов расширяется профессией. events не переписывается. Используется execute, чтобы DDL не сделал неявный commit. Повторное открытие новую схему распознаёт и перенос не повторяет; отказ откатывает схему и данные. Тесты миграции создают временную БД точной прежней схемы.

Путь по умолчанию — data/memory.sqlite3 от корня исходников; переопределяется MEMORY_DB_PATH. SQLite использует secure_delete=ON, журнал DELETE, таймаут блокировки 3 секунды.

`/reset` очищает только историю активного профиля и пишет history.reset; факты остаются. `/forget` одной транзакцией удаляет факты и события активного пользователя, затем его историю. Новое персональное событие удаления не создаётся. Подтверждение появляется после commit. Другие профили не затрагиваются. Команда не удаляет резервные копии, историю терминала или RAM других процессов; для одного профиля нужен один процесс.

## Конфигурация и отказы

Переменные: GROQ_API_KEY, GROQ_MODEL (по умолчанию openai/gpt-oss-20b), MEMORY_DB_PATH, GROQ_TIMEOUT_SECONDS (20; диапазон 1–120). Окружение перекрывает .env, включая пустые значения. Ключ хранится в SecretStr и не выводится конфигурационными ошибками. Оба запроса используют Groq; экстрактору нужна модель со строгими Structured Outputs. Используются отдельные обычные запросы, без streaming и удалённого исполнения инструментов; операции SQLite выполняет код.

При пустом ключе SDK-клиент не создаётся. Ошибки ключа, недоступности API, сети, таймаута или некорректного сетевого ответа дают «Сервис временно недоступен», не меняют факты/историю и не останавливают цикл CLI. Повторы SDK отключены. Адаптер допускает один повтор для сетевой ошибки, 408/409/429/5xx: задержка 0,5 секунды или Retry-After до 2 секунд. Постоянные ошибки вроде 400/401 не повторяются. Проверка памяти может отдельно вызвать повтор извлечения: ход иногда занимает несколько таймаутов.

После двух отказов проверки памяти выводится отдельное сообщение «Не удалось проверить изменения памяти. Ничего не сохранено…», генерация ответа не вызывается. Ошибка commit даёт «Не удалось сохранить данные. Повторите сообщение». CLI обрабатывает ошибки локальных операций с БД и продолжает работу; невозможность открыть БД или некорректная конфигурация при старте возвращает код 1. Ошибка записи отдельного диагностического события не обрывает CLI.

## События

Лог — только таблица events. Время UTC, user_id, тип и JSON записываются вместе. Успешный ход содержит memory.read, выполненные memory.add/update/delete, затем turn с request/response. /memory пишет чтение, /reset — history.reset. turn.error содержит запрос, показанный ответ, безопасную категорию и HTTP-статус. memory.error содержит этап extraction_validation, безопасный код причины и ответ, без сырого входа Pydantic. storage.error отмечает отказ commit. Успешные события транзакционны; отдельная диагностика и события локальных команд записываются по возможности.

Ключ, заголовки авторизации и сырые тела сетевых ошибок код не логирует. Тексты диалога и значения фактов являются персональными данными. Просмотр в режиме read-only описан в README. Отдельные логи и БД исключены из публикации.

По отчёту предыдущей проверки положительные сценарии проходили раздельно; непрерывный прогон прерывался HTTP 400/429. Полного успешного непрерывного живого прогона нет. При подготовке публикации новых запросов Groq не выполнялось.
